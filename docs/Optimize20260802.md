# swoolefy 框架问题修复技术方案

> 依据：`docs/测试.md`  
> 覆盖范围：审计报告中的 52 项问题。  
> 实施原则：只做局部修复、边界收紧和测试补齐，不引入大型功能，不在同一批次混入无关重构。

## 一、修复目标

本方案用于把审计项转化为可编码、可测试、可灰度、可回滚的修复任务。最终目标如下：

1. 消除会导致连接误断、请求悬挂、动态进程失控和并发上限失效的 P0 问题。
2. 明确 HTTP、Task、Event、Timer、Coroutine 的资源生命周期，避免对象和上下文残留在常驻进程中。
3. 收紧鉴权、中间件、RPC 反序列化、日志追踪等安全边界。
4. 修正 MQTT、Socket.IO、WebSocket、TCP/RPC 的协议状态与集群一致性问题。
5. 让脚手架、Composer、PHPUnit 和 CI 能对后续修改形成稳定门禁。

## 二、实施约束

### 2.1 兼容性原则

- 公共方法不直接删除；必须调整时先保留兼容入口，并标记 `@deprecated`。
- 新增配置必须提供安全默认值，旧配置文件不修改也能启动。
- 安全问题采用 fail closed：中间件缺失、非法 Token、未知 Health 类型不得静默放行。
- 生命周期清理统一放在 `finally` 或唯一结束入口中，并保证幂等。
- Context 只传播 scalar、array、null；不得把连接、SDK Client、Closure 或业务对象快照到子协程和异步任务。
- 协议修复优先复用已有 Session、Store、Heartbeat、TimeoutGuard，不新建平行状态系统。

### 2.2 提交与发布原则

- 每个阶段独立提交、独立回归，不把 52 项压成一次发布。
- 每个问题至少包含一个能在修复前失败、修复后通过的测试。
- P0 和安全修复先发布补丁版本；配置和行为兼容性调整进入次版本。
- 涉及进程、连接和协议状态的修改必须在 Linux、PHP 8.4、Swoole 6.1 环境验证。

### 3.1 TCP close 只删除当前连接半包

涉及文件：

- `src/Tcp/TcpServer.php`
- `src/Rpc/Pack.php`

实施：

1. TCP close 回调将 `Pack::destroy()` 改为 `Pack::delete($fd)`。
2. 保留 `Pack::destroy()`，但只允许 WorkerStop、Server shutdown 等进程级清理入口调用。
3. `delete($fd)` 必须幂等，fd 不存在时直接返回。
4. 增加注释说明 `destroy()` 会清理全部 fd，禁止在连接级事件中使用。

测试：

- 构造两个 fd 的半包缓存，关闭第一个 fd 后断言第二个缓存仍存在。
- WorkerStop 调用 `destroy()` 后断言所有缓存被清空。
- 重复删除同一 fd 不抛异常。

验收：

- 任意单连接断开不再关闭其他 TCP/RPC 连接。
- Worker 退出时仍能完整清理半包缓存。

### 3.2 修正动态进程类型和计数时机

涉及文件：

- `src/Worker/MainManager.php`
- 动态进程 DTO 或进程元数据类

实施：

1. `forkNewProcess()` 增加明确的进程类型参数，默认值保持现有静态进程语义。
2. 动态扩容入口必须传入 `PROCESS_DYNAMIC_TYPE`，禁止在方法内部固定写 static。
3. `destroyDynamicProcess()` 只选择 dynamic 类型进程。
4. 发出停止信号时只标记 `stopping`，不得立即减少存活计数。
5. 在 SIGCHLD/reap 确认子进程退出后，再从注册表删除并更新计数。
6. 对重复停止请求、进程已退出和 PID 不存在做幂等处理。

测试：

- 扩容后新进程 `isDynamicProcess()` 为 true。
- 缩容只停止 dynamic，不停止 static。
- 发信号后、reap 前计数不变；reap 后计数减少一次。
- 同一 PID 重复回收不会产生负数计数。

### 3.3 WorkerService 请求必须结束响应

涉及文件：

- `src/Http/HttpServer.php`

实施：

1. request 回调的所有分支最终都必须进入业务处理或显式 `response->end()`。
2. Cron/Daemon + HTTP 控制面继续走现有处理器。
3. 其他 WorkerService 组合统一返回 HTTP 503，响应体使用固定错误码 `worker_service_http_unavailable`。
4. 响应增加 `Content-Type: application/json`，不得暴露内部服务类型和配置。
5. 启动日志对不支持的组合记录一次 warning；不直接阻止启动，以降低兼容风险。

测试：

- 覆盖普通 HTTP、Cron 控制面、Daemon 控制面和无处理器 WorkerService。
- 断言每种分支只调用一次 `end()`。
- 无处理器组合在短超时内收到 503，不再悬挂。

### 3.4 CommandRunner 使用真实启动时间判断超时

涉及文件：

- `src/Core/CommandRunner.php`
- `RunProcessMetaDtoWorker`

实施：

3. 只有进程实际超过配置超时，才允许走现有超时恢复逻辑。
4. 达到并发上限且未超时必须拒绝启动新进程。
5. 对空进程列表、缺失旧数据字段和系统时间回拨做防御处理。

测试：

- 达到并发上限、所有任务未超时时返回不可启动。
- 最老任务超过超时时进入恢复分支。
- DTO 不再产生未定义属性 warning。
- 并发数在压力测试中不超过配置上限。

### 4.1 TaskController 统一结束

涉及文件：

- `src/Http/HttpAppServer.php`

实施：

1. `onTask()` 将 TaskController 创建、执行和清理放入同一个 `try/finally`。
2. `task_enable_coroutine=false` 时，在 `finally` 调用 `end()`。
3. 已由 coroutine defer 接管的 Controller 不重复结束。
4. `end()` 必须幂等，业务异常和清理异常分别记录，清理异常不得覆盖原始异常。

测试：

- 成功、业务异常、反序列化异常三条路径都释放 Application 和组件。
- 连续执行大量 Task 后，Application 注册数量和连接池借出数回到基线。

### 4.2 为同步 EventApp 提供唯一运行入口

涉及文件：

- `src/Core/EventApp.php`
- `src/Core/EventController.php`
- 所有直接创建 EventApp/EventController 的同步事件入口

实施：

1. 新增 `EventApp::run(callable $callback)`，内部负责注册、执行和 `finally end()`。
2. `cid < 0` 时由 `run()` 主动结束；协程内继续使用 defer。
3. ManagerStart、PipeMessage、Finish 等入口改用 `run()`。
4. 保留原构造方式一个兼容周期，但增加 deprecated 注释和开发环境 warning。

测试：

- 同步事件成功和异常后，`Application::$apps[-1]` 均不存在。
- 组件销毁和连接归还只执行一次。

### 4.3 防止 EventApp 覆盖当前请求 App

实施：

1. `registerApp()` 检测当前 cid 是否已绑定 Application。
2. 如果已绑定对象不是当前 EventController，抛出明确的生命周期异常，提示使用 `goApp()`。
3. 同一对象重复注册允许幂等返回。
4. 禁止通过覆盖映射“修复”冲突。

测试：

- HTTP 请求协程直接创建 EventApp 时失败，原 HTTP App 保持不变。

### 4.4 Context 空环境边界

涉及文件：

- `src/Core/Coroutine/Context.php`
- `src/Core/Func/function.php`
- `src/Core/Task/AsyncTask.php`

实施：

1. 增加 `Context::snapshot(): array`；无协程且无 Application 时返回空数组。
2. `goApp()`、AsyncTask、Timer/Cron 只通过 `snapshot()` 读取可传播数据。
3. `Context::set()` 在没有有效上下文容器时抛出明确的 `ContextUnavailableException`，避免写入进程级静态共享区造成串数据。
4. `get()` 在无上下文时按传入默认值返回，`has()` 返回 false，`delete()` 幂等。
5. 不使用进程全局 `ArrayObject` 作为 fallback。

测试：

- 普通 CLI、启动阶段和 Timer 中调用 snapshot 不触发 TypeError。
- 无上下文 set 给出可诊断异常。
- 子协程只得到允许传播的数据副本，修改不反向污染父协程。

## 十、测试体系与验证矩阵

### 10.1 单元测试

重点覆盖纯逻辑和失败边界：

- Pack fd 隔离、包长和二进制切片。
- Context snapshot、Hook cid、ComponentTrait。
- CommandRunner 时间判断、PushDeliveryResult ACK。
- JSON parser、CORS、Optional Auth、Trusted Proxy。
- MQTT Session 限额、协议级别和 keep_alive。

### 10.2 协程与生命周期测试

- Task/EventApp 在成功、异常、超时后的资源释放。
- Parallel / GoWaitGroup：保持原实现，本阶段不新增并发上限与非 failFast 错误可见性用例。
- AsyncTask、Cron、Tick 不传播对象和请求身份。
- Job TimeoutGuard 和连接池归还。

### 10.3 HTTP 集成测试

启动真实测试服务器，通过 HTTP Client 验证：

- WorkerService fallback 不悬挂。
- 中间件早于 Validation。
- 非法 JSON、缺参脱敏、Trusted Proxy。
- Optional Auth 的缺失 Token 与非法 Token 差异。
- afterRequest 异常路径仍保存 Session。

### 10.4 协议集成测试

- 两个 TCP 客户端分别制造半包，关闭其中一个验证另一个不受影响。
- RPC 发送恶意长度、对象序列化和二进制 payload。
- MQTT V3/V5 混合连接、QoS2 pending、keep_alive。
- Socket.IO 跨节点 polling/upgrade 和二进制附件过期。
- WebSocket open 后立即首包以及共享存储失败。
- Redis Streams 多目标部分成功。

### 10.5 进程级测试

- 动态扩容、缩容、重复 reap 和计数一致性。
- graceful shutdown 在预算内排空。
- confctl 多进程并发写。
- CreateCmd 各失败路径退出码和原子生成。

### 10.6 常驻进程稳定性

每个阶段至少执行一次持续运行测试，采集：

- Application/Context 注册数量。
- 连接池借出数和归还数。
- Worker RSS、Table 行数、静态缓存项数。
- TCP 半包、MQTT pending、Socket.IO assembler 数量。
- 动态进程数、CommandRunner 在途数。

稳定状态下这些指标应回到固定基线或有明确上限，不得随请求数线性增长。

## 十一、配置变更

本方案允许新增以下可选配置，均必须提供默认值和配置 Stub：

- HTTP：`trusted_proxies`。
- MQTT：QoS2 pending 最大条数、最大字节、TTL。
- WebSocket/Socket.IO：二进制附件 TTL、opening 超时。
- Health：单项检查超时。
- Nacos：`stale_ttl`。
- OpenTelemetry：header 白名单、attribute 最大长度、受控 body 采样。

配置读取要求：

1. 启动时完成类型、范围和组合校验。
2. 数值必须大于 0 的配置不得接受 0 或负数。
3. 未配置时使用框架安全默认值。
4. 未知配置类型不得在运行期静默忽略。

## 十二、可观测性要求

新增或修正以下结构化指标：

- `tcp_partial_buffer_count`
- `worker_dynamic_process_count`
- `command_runner_inflight`

- `context_propagation_rejected_total`

## 十三、灰度、回滚与故障处置

### 13.1 灰度顺序

1. 单 Worker 测试环境。
2. 多 Worker 单节点。
3. Redis/Nacos 等共享状态开启的双节点。
4. 小流量生产节点。
5. 全量发布。

### 13.2 回滚边界

- 每个阶段独立发布，因此只回滚当前阶段，不回滚已验证的 P0 补丁。
- 配置新增项均有默认值，回滚代码前先停止使用新配置。
- confctl 文件格式不做破坏性升级。
- Redis sid、Stream 和 Workflow Store 不改变持久化格式；如必须调整，需另出迁移方案。

### 13.3 自动停止灰度条件

出现以下任一情况立即停止扩量：

- 请求悬挂数、异常关闭数或 5xx 明显上升。
- Worker RSS 持续线性增长。
- 动态进程数超过配置上限。
- MQTT/WebSocket 重连率明显上升。
- Streams pending 或失败重试持续堆积。
- Session、Workflow Run 或用户推送出现跨 Worker 不一致。
